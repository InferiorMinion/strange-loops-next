The invariant under every step: records hold lineage ids, never names. Each step only adds records or changes how names resolve. Nothing already written is ever rewritten.

Why a new lineage instead of renaming the seat
  • The seat was shared by every session and every model. Renaming it would hand Wren work done by sessions that never became Wren.
  • A new lineage plus adoption is honest retro-claiming. The seat's records stay as written. Wren's adoption is a new, dated, signed record pointing at them.
  • Rename stays right when a lineage is already one continuous thread, for example Wren choosing a different name later.
  • At session start, a session becomes Wren by loading Wren's compiled self. Wren's key signs its records, and the session says what it is in a record. Continuity is held by the store, not by any one session.

8 · Orchestration: a request goes out, a tick comes back

proposal Kyle's scenario, 2026-11-10. Work is asked for by emitting a record, not by filing an issue. An orchestrator plans it, hands tasks to short-lived sessions, and returns one covering record that unpacks down to each session's detail.

Cases already holds the vertex templates for this under "Task orchestration": a vertex per subagent, slice and orchestrator, each ticking at a boundary and covering its children's ticks. This step walks it with observers and stores, and tests it against what is built.

WhoWhat it isWhat it writes

Implementers, reviewers, merge handlerssessions: a key each, no lineagetask status, questions, results, under their assignment

  1. A request is emitted. An ordinary record about the repo or the thing. It is not a tick: nothing is covered yet.

  2. A vertex lists requests nobody has taken. A request's arrival is its boundary. The orchestrator takes one by revising it. Two orchestrators taking the same request is a fork, and shows as one.

  3. The orchestrator plans. One changeset: a plan and its tasks. Each assignment names a task and a session's key, so the plan tree and the launch tree are one tree.

  4. Sessions work. Each writes as its own key, under its assignment, and ends with a task-complete marker, which is its vertex's boundary. A question goes up as a record about the task; the orchestrator answers it or passes it to you. Recall records the detail underneath.

  5. The ticks climb. A session's tick is covered by its slice's, and the slices' by the orchestrator's, which ticks when all of them have and lands into the requester's store. Unpacking is walking the covers back down: goal, slices, sessions, recall.

Only two lineages are needed. You and the orchestrator. A session is a key that writes as itself, which the model already counts as its own word. A session that grows into a lasting collaborator signs an anchor later, and its key becomes that lineage's root key.

The dry run: what today's CLI could and couldn't do

Replayed with loops as merged on 2026-11-10: one open store, six keys, 25 records, using the day's real CI work as the content. Every line verified.

The slice reads no boundary, ticks, param or into, so the run could not use the Cases templates. It stood in plans, tasks and a closing summary as ordinary records about each other. Some of what broke is that stand-in showing why the design uses ticks.

The three breaks are decision D8 in the roadmap. D8a and D8b are built in the model, the vectors, JavaScript and Rust. A record is an emit of one thing, the one of names, or its own id; about only mentions and never makes a head. A task about its plan, a record about another task, and a closing record about the ids it covers no longer head those things. Of D8c, declared keys, sets and the slots that follow keys are built: a count of open tasks reads each task by its live setters. So is the writer's anchor rule: loops emit names every live record of the thing it holds and carries the thing's whole about. The slice laws are proved, for one keyed thing and for a spec with a keyed slot. The table records the run as it was.

What it needs that doesn't exist
  • Ticks, and a runner for boundaries. The spec grammar carries boundary, ticks, param and into, and nothing reads them. The tick itself waits on D7, the result encoding, which now blocks this as well as retiring.
  • Something that acts when a boundary fires. The earlier prototype's boundary could carry a command to run, which is what made its cascades start work by themselves. Here a boundary says when a vertex ticks, and "a vertex never signs anything; the observer who ran it signs". So starting a session is an observer's act, and which observer watches which vertex is not designed.
  • Where a question or a note about a task goes. Covers handle "belongs to" for work. A record that is only about a task no longer competes to be its state (D8b), and a fold that asks what was said about the task still finds it.
  • Delegation, for strict stores. In an open store an assignment is just context. In a store that admits only granted writers, the orchestrator's grant must let it sponsor sessions, and authority must only narrow on the way down.
  • Covers across stores. Preferences, tasks, recall and the repo are likely separate stores. A reader without one of them gets "unknown" for that branch.
  • Who signs recall's capture. Signed by recall, a transcript is recall's claim about a session. Signed by the session, it is the session's own word.
